# 設計の意図

各節は、その設計が守っているもの、引き合っている力、それが続く限り採らない案、同じ種類の次の判断の決め方、その判断を覆す観察できる事実を書く。前提が変わったら、その節を書き換える。

## ハードウェアモデルは直接型 LFSR

守っているもの: 画面に出るレジスタの初期値が、プリセットの `init` と同じ値であること。

- Rocksoft モデルの `init` は、直接型 LFSR の初期レジスタ値として定義されている。入力ビットを最上位ビットの出口で XOR し、その結果をフィードバックにする形なら、`init` をそのままレジスタに入れられる。
- 表示中の計算は、reveng カタログの `check` 値でそのまま確かめられる。
- 最初のクロックから `fb = 1` が起こりうるので、序盤のスロー再生でもフィードバックが動いて見える。

採らない案: 入力の末尾に width 個の 0 を付け足し（augmentation）、LSB 側から押し込む形。多項式の筆算とは対応しやすい。しかし `init ≠ 0` のときは `init` を別の値に変換しないと同じ CRC にならず、その変換を説明する画面が別に要る。また最初の width クロックは最上位ビットが必ず 0 なので、フィードバックが一度も動かない。両方の形を切り替えて見せる案も、同じ理由で採らない。

次の判断: 図や擬似コードに新しい値を出すときは、プリセットのパラメータがそのまま画面に出る形を選ぶ。

見直す条件: `init` を直接型 LFSR の初期レジスタ値として定義しないカタログから、プリセットを取るようになったとき。

確かめているテスト: `src/domain/trace.test.ts` の「the first step loads init into the register」と、`src/domain/equivalence.test.ts` のカタログの `check` 値の照合。

## 描画はステップ番号の純粋関数

守っているもの: 利用者が CRC 設定を変えても、一時停止・コマ送り・逆再生・シークが同じ仕組みで動くこと。

- アプリは Vite + React + TypeScript の SPA で、計算済みのステップ列を SVG で描く。ステップの間の動きは CSS transition で補う。
- 設定が変わるとステップ数、つまりアニメーションの長さも変わる。そのときはステップ列を作り直すだけで済む。

採らない案: Motion Canvas で動画として作り、Player に variables で設定を渡す形。尺の計算のし直しや、外側の UI との連携を、Player の制約の中で行うことになる。

次の判断: 再生に関わる新しい表示は、ステップ番号と設定から決まる値として作り、時間で進む状態を持たせない。

見直す条件: 再生中の操作で、その後のステップを変える必要が出たとき。たとえば、アニメーションの途中で入力ビットを反転する場合。

## LFSR 図はステップの分け方に従う

守っているもの: 図の各ステップが、同時に強調される擬似コードの 1 行と同じことをしていること。

- 1 クロックは、擬似コードの行に合わせて `shift`（`crc = (crc << 1) & mask`）と `xor`（`crc ^= poly`）の 2 ステップに分かれる。ハードウェアの LFSR は、これを 1 クロックで `r'[i] = r[i-1] XOR (feedback AND poly[i])` として計算する。
- 箱はすべて横線でつなぐ。`shift` では全ての値が真横に滑る。
- XOR ゲートは `poly[i] = 1` の各 `r[i]`（`i = 0` を含む）の真下に置く。`xor` では `r[i]` の値と下から来るフィードバックがゲートで合流し、結果が `r[i]` に戻る。`xor` の入力は、画面に見えている箱の今の値とフィードバックそのものになる。

採らない案:

- 教科書の図のように、ゲートを `r[i-1]` と `r[i]` の間に置く形。`xor` のステップではシフトが済んで `r[i-1]` に別の値が入っているのに、図は `r[i-1]` とフィードバックの XOR を `r[i]` に入れるように見える。また `shift` のステップでは、タップの位置の値がゲートの下をくぐって移る。
- 箱の間の Y 字を残し、`shift` だけ横に滑らせる形。横線と Y 字の 2 つの経路が並び、値がどちらを通るのか分からなくなる。

次の判断: 図の動きを足すときは、その動きが擬似コードのどの行に当たるかを先に決め、行と 1 対 1 にならない動きは描かない。

見直す条件: 擬似コードが 1 クロックを `shift` の行と `xor` の行に分けなくなったとき。

確かめているテスト: `e2e/diagram.spec.ts`。

## `main` は CI を通った pull request でだけ変わる

守っているもの: crc.shortarrow.jp に公開されるのが、型検査・単体テスト・E2E テストを通った commit だけであること。また、GitHub に Cloudflare の認証情報を置かないこと。

- 作業は短命のブランチで行い、pull request で `main` にマージする。
- `main` のルールセットは、`main` に追いついたブランチで CI のチェック `test` が通ることをマージの条件にする。このため、マージ後の内容そのものがテスト済みになる。
- Cloudflare Workers Builds は GitHub App でリポジトリにつながり、`main` を本番のブランチとして公開する。ほかのブランチは preview としてビルドし、それぞれの preview URL に出す。Workers Builds は push されたブランチを CI を待たずに公開するので、テスト済みであることはルールセットが受け持つ。
- private のリポジトリでルールセットを使うには GitHub の有料プランが要るので、リポジトリは public にしている。

採らない案:

- CI の後に GitHub Actions から公開する形。Cloudflare の API トークンをリポジトリのシークレットに置くことになる。Cloudflare は GitHub の OIDC トークンを受け付けないので、短命の認証情報には置き換えられない。
- `main` に直接 push し、CI の後に commit を `production` ブランチへ進めて Workers Builds に公開させる形。シークレットは要らない。しかしブランチとジョブが 1 つずつ増え、テストを通っていない commit も `main` に入る。
- `main` に直接 push し、Workers Builds に `main` を公開させる形。テストに落ちる commit が、CI が終わる前に公開される。

見直す条件: Cloudflare が GitHub の OIDC トークンを受け付け、GitHub Actions からの公開に長命のシークレットが要らなくなったとき。または、Workers Builds が GitHub のチェックが通るまで公開を待てるようになったとき。

確かめているもの: `main` のルールセットが求めるチェック `test`（`.github/workflows/ci.yml`）。
